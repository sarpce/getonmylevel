# Interface design

Design interfaces around the people using them and the work they need to do. Make visual choices intentional, keep the system coherent, and refine the implemented result against its purpose.

## Understand the work

Before proposing changes, inspect the brief and relevant project to understand the interface's purpose, audience, key tasks, content, platform, constraints, and existing design system. Treat provided designs, existing components, and tokens as sources of truth where they apply.

For a new interface or substantial redesign with unresolved subjective visual direction, offer multiple meaningfully different directions grounded in the brief. Explain how each would use typography, color, layout, and imagery, along with practical tradeoffs and the balance between expressive character and usability. Wait for the user's selection before design-dependent implementation. Honor an explicit direction or prior decision; reopen it only when a relevant change warrants discussion. Do not ask for a direction on a narrow implementation task, a review-only request, or an established design where no aesthetic change was requested. If interaction is unavailable and no direction is authorized, report the choice as unresolved instead of silently choosing.

## Establish and apply the system

Before implementation, establish a coherent, task-appropriate design system. Reuse and extend existing tokens and components first. Where the project has no applicable system, define only what the work needs: typography roles and scale, color roles, spacing and layout rules, component states, and relevant choices for radii, elevation, iconography, and motion. Choose values deliberately and apply them consistently. Let the system evolve as each task needs; do not impose a universal font, scale, or aesthetic. Document decisions in the project's existing conventions when useful, without creating unsolicited documentation.

Give content a clear hierarchy. Keep text legible, group related information meaningfully, make controls predictable, and use responsive layouts that fit the target platform. Provide relevant empty, loading, error, disabled, focus, hover, and active states. Do not invent functionality or factual content.

Build accessibility into the interface: use semantic controls, support keyboard access with visible focus, maintain readable contrast, provide appropriate target sizes, respect text scaling, and account for reduced motion where relevant. Follow applicable platform conventions and user requirements without claiming formal compliance or applying universal platform measurements without context.

Use motion, images, decoration, and visual patterns for reasons grounded in the brief. Treat familiar templated defaults as prompts to review whether a choice serves the product, not as categorical prohibitions.

## Review

Review the result against the chosen direction, user tasks, system consistency, interaction states, responsiveness, and accessibility. Use rendered inspection or other verification only when explicitly requested or permitted by the user and repository instructions. Report what was actually checked and distinguish observed findings from assumptions that remain unverified.

Respect explicit user instructions, the selected development mode, repository conventions, other applicable skills, and tool permissions. This skill does not authorize external writes or new dependencies.
