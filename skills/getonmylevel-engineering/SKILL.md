# Software engineering

Follow the user's explicit instructions and repository policies. Inspect relevant code and nearby conventions before changing things. Make the smallest coherent change that addresses the request. Prioritize correctness, readable maintenance, clear interfaces, security, appropriate failure handling, and scope discipline. Avoid speculative abstractions and unnecessary dependencies.

Verify only as requested or permitted by the active instructions. Choose checks that meaningfully establish the changed behavior. Do not claim checks that did not run. Do not add tests unless requested or allowed by the active task workflow.

For every new request involving any software or code edit, including fixes, tests, configuration, documentation, and skill instructions, prompt the user to choose Simple or Agentic mode before editing or delegating, regardless of size or a choice made for an earlier request. Read-only investigation may continue while the answer is pending. Record the actual answer for this request; do not edit or delegate until it arrives. Simple means working directly; Agentic means using agents subject to the active session's delegation rules. Wait for the actual answer; a preselected option, default, timeout, or elapsed time is not an answer. Use a choice interface only when it can deliver the response; otherwise ask in chat and leave dependent work pending. If Agentic mode is unavailable or disallowed, explain why and ask how to proceed instead of silently switching modes. Respect higher-priority instructions.

When Agentic mode is selected, use the installed getonmylevel agent roles configured for the active client: `getonmylevel_designer` and `getonmylevel_implementer`, with `getonmylevel_reviewer` and `getonmylevel_tester` only when the user opts into those roles. Claude Code uses the corresponding hyphenated names. These predefined agents are in the getonmylevel agent skillset, separate from the skills. Set each spawned agent's type to its installed getonmylevel role. A task-specific spawn name or identifier may be chosen freely; it does not change the required agent type. If a required configured role is unavailable, explain which one is missing and ask the user how to proceed. Ask separately whether the user wants an independent reviewer and tester; each is disabled unless selected. Wait for actual answers before assigning those optional roles. Then follow the agent workflow, subject to higher-priority instructions and tool availability.

For agent-based work, preserve user control over independent review and testing: ask separately whether the user wants an independent reviewer and an independent tester, with each disabled unless selected. Ask only when the choice is relevant and not already answered. Use available choice interfaces when useful, and wait for actual answers before dependent work. Do not prompt inside a delegated role.

Read [agent-workflow.md](references/agent-workflow.md) when using the agent-based workflow.

## Development environments and machine settings

Before proposing an installation or environment change, inspect the relevant project configuration, version files, lockfiles, active environments, and available tools. Treat them as evidence of project intent, not authorization to install or modify anything. Use terms that distinguish runtime installation and selection, version-manager settings, project environments, project dependencies, globally installed tools, and temporary one-off tools. Ecosystems differ: do not imply a tool supports a scope it does not.

Before each installation, dependency or environment configuration, IDE, shell, PATH, environment variable, container, remote-host, account, or system change, get the user's choice of applicable scope and exact target unless they already explicitly chose those for that specific action. Offer only scopes the tool supports and that fit the task: for example, an existing or new project environment, a project-local dependency, a user-wide or system-wide installation, or a specific workspace, profile, remote, or container. State the proposed action, target, intended version or constraint where relevant, affected files or settings, and material consequences. Recommend an option when useful and explain why. Call out effects on shared defaults, other projects, settings sync, or workspace collaborators. Do not infer permission from project conventions or from approval of a different action; ask again if the target or scope materially changes. Wait for the actual answer before taking the dependent action; silence, elapsed time, and a preselected option are not answers. Do not repeat a choice already made for the same action.

Follow the project's package manager and lockfile conventions. Explain whether manifests or lockfiles will change, and distinguish temporary tooling from project dependencies. Avoid unnecessary dependencies. Where available, distinguish project/workspace settings, user settings, profiles, remote or container environments, and machine-wide settings; identify the IDE instance and environment affected. Treat workspace extension recommendations, workspace settings, and personal IDE configuration as separate. A recommendation does not prove an extension is installed or authorize installing, updating, disabling, or removing it. Explain workspace sharing or sync effects when relevant.

Identify whether a change affects only the current process or shell session, a shell profile, PATH, an environment variable, a container, remote host, user account, or the system. Explain its target and impact before asking the user to choose. Never expose secrets. Before adding credentials, connecting an account, or enabling a service, ask for an explicit choice and explain the action and destination.

Keep questions concise and relevant to the actual tool and environment; give enough detail for an informed choice without requiring internal implementation knowledge. Continue independent read-only work while a choice is pending. If the client cannot deliver a choice interface response, ask in chat and leave the dependent action pending. Respect higher-priority instructions, explicit user preferences, and platform permissions.
